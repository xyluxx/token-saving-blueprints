# A first change, filled in

This is an **illustrative operator walkthrough**, not a captured account, executed native task or savings benchmark. Replace its example task with one of your own. No token/cost result is invented.

## The situation

You already use Claude Code with your own native subscription. You have an existing project and its normal tests. You want less repeated repository scanning and fewer unnecessary full-file rewrites, without changing the model or account.

## Route passport

| Field | Example entry |
|---|---|
| Harness | Existing Claude Code installation; read its actual version |
| Authentication | Existing native subscription login; verify no API/managed override changes the payer |
| Model and effort | Keep the exact values observed at task start |
| Scope | One trusted disposable project or an approved working branch |
| New dependency | None |
| Proposed change | One short, scoped addition to the existing project instructions |
| Control | Instructions guide behavior; native permissions still enforce allowed operations |

Read the [Claude Code guide](../docs/harnesses/claude-code.md) before applying this example.

## Task contract

Example task: fix an identified formatting defect in an existing function. Preserve callers' behavior, locale/negative-value requirements and every project-mandated test. Read the relevant implementation and dependencies; do not select a smaller substitute after the fact.

Use the project's real acceptance tests. This example does not supply imaginary tests or claim the defect was fixed.

## One proposed instruction change

After approval, append a clearly identifiable section to the existing project `CLAUDE.md`, preserving all its prior content:

> For this task, locate exact files/symbols before broad reads. Inspect the affected implementation and dependencies. Reuse existing code and make the smallest complete patch. Run all required checks, preserve failures, and return the verified change rather than reprinting unchanged files. Do not change model, effort, authentication or permissions, and do not omit requested work.

If the project uses a different effective instruction scope, follow the actual guide and native status rather than creating a competing file. Native protected-file approval still applies.

## Verify

1. Confirm the effective model/account/effort and loaded project instruction.
2. Complete the real task through the native approval flow.
3. Check the diff, complete test results and required behavior.
4. Record available usage, errors, rereads and repair. If token/quota data is unavailable, mark it unknown.
5. Compare against an equivalent baseline before claiming savings.

No native task or comparison was executed for this illustration. Its purpose is to make the procedure concrete.

## Roll back

Remove only the section you added, preserving any later user edits. Reload or reopen through the documented native mechanism if required. Verify the previous setup remains effective. Review task-file rollback separately; removing an instruction does not undo code changes, remote actions or charges.

## What this example shows

A useful first change can be a small operating practice through an existing harness, not an installation. Keep it only if it helps your complete task. If your agent already follows this discipline, extra instructions may add overhead and should be omitted.
